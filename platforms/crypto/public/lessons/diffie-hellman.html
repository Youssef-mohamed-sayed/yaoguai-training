    Diffie–Hellman

    Intermediate

    In this lesson you will learn:

    • Why two strangers need a way to agree on a secret before any symmetric cipher can be used
    • The discrete logarithm problem, and why it makes the exchange one-way-secure
    • Why plain Diffie-Hellman has no authentication, and what Man-in-the-Middle means here
    • How this sets up everything RSA (next module) builds on

    Introduction

    Every cipher so far assumed both sides already share a secret key. But how do two people who've never met, talking over a channel an attacker can fully observe, agree on a secret key in the first place? Diffie–Hellman answers exactly that question — it's not encryption at all; nothing confidential is ever sent. It's a key exchange: a way to end up with the same secret number on both ends, without ever transmitting that number.

    Note on sourcing: this module extends beyond the provided course slides — it's included because it's the conceptual bridge every real-world RSA/TLS deployment relies on, and the course's progression (symmetric → asymmetric encryption) doesn't fully make sense without it.

    History

    Published in 1976 by Whitfield Diffie and Martin Hellman (with foundational contributions from Ralph Merkle), this was the breakthrough that created modern public-key cryptography as a field. Before it, every known cipher — including everything in this course so far — needed the two parties to somehow securely share a key beforehand, which is itself a hard logistical problem at scale. Diffie–Hellman solved "how do we agree on a secret over a public channel," which directly enabled RSA (covered next) and everything built on it — it's the reason your browser can set up a secure HTTPS connection with a server it's never talked to before.

    Brief definition

    DEFINITION

    Diffie–Hellman lets two parties, communicating only over a public channel, compute an identical shared secret number — without ever sending that secret, and without an eavesdropper who sees every message being able to compute it too.

    ASYMMETRIC / PUBLIC-KEY CRYPTOGRAPHY

    Cryptography where the two parties don't use the same secret value the same way — unlike XOR, RC4, DES, AES (all symmetric), here each side keeps something private and shares something else publicly.

    It relies on a mathematical one-way street: given a prime p, a base g, and a secret exponent a, computing g^a mod p is fast — but working backwards from g^a mod p to recover a (the "discrete logarithm problem") is, for large enough numbers, computationally infeasible.

    How it works

    Agree publicly: p, g→Each picks a secret (a, b)→Exchange g^a mod p and g^b mod p publicly→Each computes the same shared secret

    Step by step, for Alice and Bob:

    1. Publicly agree on a large prime p and a base g — these can be sent in the clear, an eavesdropper seeing them learns nothing useful alone.
    2. Alice picks a secret number a, keeps it private, and sends Bob A = g^a mod p.
    3. Bob picks a secret number b, keeps it private, and sends Alice B = g^b mod p.
    4. Alice computes B^a mod p. Bob computes A^b mod p. Both equal g^(ab) mod p — the same shared secret, computed independently.

    An eavesdropper who saw p, g, A, and B still can't compute g^(ab) mod p without solving the discrete logarithm problem to recover a or b — which, for properly sized numbers, is considered infeasible with current computing power.

    TASK 01predict output (small numbers, for intuition only — not secure sizes)

    Using p=23, g=5: Alice's secret is a=6, so she sends A = 5^6 mod 23 = 8. Bob's secret is b=15, so he sends B = 5^15 mod 23 = 19. Alice computes the shared secret as B^a mod 23 = 19^6 mod 23. What does Bob compute, and does it match?

    Bob computes A^b mod 23 = 8^15 mod 23, and it's a different number
    Bob computes A^b mod 23 = 8^15 mod 23, and both sides land on the same value (2, in this toy example)

    Diffie–Hellman in Python

    This isn't one of the existing Flask API's endpoints (there's no key exchange protocol to expose via a stateless HTTP call) — the snippet below is a minimal, standalone illustration, not production code. Real deployments use much larger primes (2048+ bits) and standardized parameter groups.

    import secrets

p, g = 23, 5   # toy values — public, agreed in advance

# Alice's side
a = secrets.randbelow(p)
A = pow(g, a, p)

# Bob's side
b = secrets.randbelow(p)
B = pow(g, b, p)

# exchange A and B publicly, then:
alice_shared = pow(B, a, p)
bob_shared   = pow(A, b, p)
assert alice_shared == bob_shared   # both landed on the same secret

    Practical tasks

    TASK 03multiple choice

    Does Diffie–Hellman encrypt any actual message content?

    Yes, it's a full encryption scheme
    No — it only establishes a shared secret, which is then typically used as a key for a symmetric cipher like AES

    Strengths

    • Solves the key-distribution problem outright — no prior shared secret, no trusted courier, no pre-shared key file.
    • Forward secrecy (when fresh keys are used per session, "ephemeral" Diffie–Hellman) — even if a long-term key is later compromised, past session keys stay secret.

    Weaknesses

    Algorithm weakness — no authentication: plain Diffie–Hellman, by itself, doesn't verify who you're actually exchanging keys with. This opens the door to a Man-in-the-Middle (MITM) attack: an attacker intercepts and relays the exchange, establishing one shared secret with Alice and a different one with Bob, while Alice and Bob believe they share one secret directly with each other. Real protocols (TLS) bolt on authentication (certificates/signatures) specifically to close this gap — Diffie-Hellman alone is not enough.

    Implementation weakness — weak or reused parameters: using a small or poorly chosen prime p, or reusing the same p/g across huge numbers of connections (as the real-world "Logjam" attack exploited in 2015), can make the discrete-log problem tractable in practice even though the algorithm itself is sound.

    Cybersecurity & CTF perspective

    Diffie–Hellman CTF challenges typically target small or badly chosen parameters (a weak prime, a tiny private exponent) that make the discrete logarithm solvable in practice, or they directly stage a Man-in-the-Middle scenario to test whether you understand why authentication matters. This module is also the conceptual hinge the course needed: everything before this point was symmetric (one shared key); everything from RSA onward is asymmetric (different keys for different roles) — Diffie–Hellman is the bridge that shows why asymmetric ideas were needed at all.

    CTF Challenge

    CHALLENGE · SMALL PRIMEIntermediate
    SCENARIO

    A toy implementation uses p=23, g=5. You observe Alice's public value A=8 on the wire.

    OBJECTIVE

    Because p is small, brute-force every possible private exponent a (0 to 22) to find Alice's actual secret: the value of a such that 5^a mod 23 = 8.

    FLAG FORMAT

    flag{a} where a is the recovered secret exponent

    Hint 1

    With such a small prime, you can just try every exponent 0–22 with pow(5, a, 23) and check which one gives 8.

    Show solution
    PYTHON
    for a in range(23):
    if pow(5, a, 23) == 8:
        print(a)   # 6
        break
    WHY THIS MATTERS

    This is exactly why real Diffie–Hellman uses primes thousands of bits long — brute-forcing the exponent (or solving the discrete log problem any other known way) becomes computationally infeasible at that scale.

    Summary

    • Diffie–Hellman establishes a shared secret over a public channel — it's a key exchange, not encryption itself.
    • Security rests on the discrete logarithm problem: easy to compute g^a mod p, hard to reverse.
    • Plain Diffie-Hellman has no authentication — vulnerable to Man-in-the-Middle without it.
    • It's the conceptual bridge from symmetric to asymmetric cryptography — RSA is next.
