    ENCRYPTION · MODULE 06 · SYMMETRIC STREAM CIPHER

    RC4

    Intermediate

    In this lesson you will learn:

    • What a stream cipher is, and how it differs from a block cipher
    • How RC4's KSA and PRGA stages turn a key into a long keystream
    • Why RC4 is formally retired — a real algorithm-level flaw, not just an implementation mistake
    • Why reusing an RC4 key reopens the exact same attack as reused XOR keys

    Introduction

    XOR taught you the core idea — plaintext XOR key = ciphertext — but a short, repeated key leaks patterns. RC4 fixes exactly that problem: instead of cycling a short key directly over the data, it uses the key to generate a long, pseudo-random keystream first, then XORs that against the data. Same core operation, much better key material.

    STREAM CIPHER

    A cipher that encrypts data one byte (or bit) at a time by combining it with a keystream, rather than processing fixed-size blocks like AES.

    History

    RC4 ("Rivest Cipher 4") was designed by Ron Rivest in 1987 for RSA Security, originally kept as a trade secret until it leaked in 1994. Its simplicity and speed made it hugely popular — it secured early SSL/TLS, WEP (early Wi-Fi security), and Microsoft protocols for over two decades. Statistical biases discovered in its keystream (certain output bytes aren't uniformly random) were gradually weaponized into practical attacks, and by 2015 the IETF formally prohibited RC4 in TLS. It is retired for anything security-sensitive today.

    Status today: Educational / Legacy / Insecure

    Brief definition

    DEFINITION

    RC4 is a stream cipher: it uses a key to generate a long pseudo-random keystream, then XORs that keystream against the plaintext, byte by byte.

    XOR (module 05)

    Key is cycled directly over the data — short, repeating, and leaky.

    RC4

    Key seeds an algorithm that generates a long, non-repeating-looking keystream — XOR is still the final step.

    How it works

    Key→KSA (scramble a 256-byte state)→PRGA (generate keystream bytes one at a time)→XOR with plaintext

    KSA — Key Scheduling Algorithm

    RC4 keeps an internal array S of the 256 values 0–255. The KSA shuffles this array using the key — for each position i, it swaps S[i] with another position chosen using the key bytes (cycled, exactly like the XOR cipher's key-cycling, reused here as one ingredient of a bigger algorithm).

    PRGA — Pseudo-Random Generation Algorithm

    After scrambling, RC4 generates the keystream one byte at a time: it swaps two more positions in S based on running counters, and outputs S[(S[i]+S[j]) % 256] as the next keystream byte. This repeats for as many bytes as the plaintext needs.

    TASK 01identify

    Which stage of RC4 actually uses the secret key?

    The KSA — the key seeds the initial shuffle of the 256-byte state
    The PRGA — the key is used while generating each keystream byte

    RC4 in Python

    stream_core.py (shape of the implementation) 
    def _rc4_ksa(key: bytes):
    S = list(range(256))
    j = 0
    for i in range(256):
        j = (j + S[i] + key[i % len(key)]) % 256
        S[i], S[j] = S[j], S[i]
    return S

def _rc4_prga(S, length):
    i = j = 0
    out = bytearray()
    for _ in range(length):
        i = (i + 1) % 256
        j = (j + S[i]) % 256
        S[i], S[j] = S[j], S[i]
        out.append(S[(S[i] + S[j]) % 256])
    return bytes(out)

    Practical tasks

    TASK 03multiple choice

    If you reuse the same RC4 key for two different messages, what happens?

    Nothing — RC4's keystream is always safe to reuse
    The identical keystream is generated both times, recreating exactly the same key-reuse vulnerability as XOR

    Strengths

    • Extremely fast and simple — no block padding, minimal state, byte-at-a-time — which is exactly why it was so widely adopted.
    • Any-length input — stream ciphers don't need block padding the way AES does.

    Weaknesses

    Algorithm weakness: RC4's keystream has statistical biases — some byte values appear slightly more often than true randomness would allow, especially in the first bytes of output. Over enough reused or related keystreams, these biases let attackers recover plaintext without ever learning the key. This is a flaw in RC4 itself, not a misuse — it's why RC4 is formally banned in TLS.

    Implementation weakness: exactly like XOR, reusing a key (and therefore a keystream) across multiple messages is catastrophic — this is precisely what broke WEP Wi-Fi security in the early 2000s.

    Cybersecurity & CTF perspective

    RC4 appears constantly in CTFs and legacy-system assessments precisely because it's still found in old code, old protocols, and old malware. Spotting "stream cipher with a short key and reused keystream" is a direct bridge from the XOR lesson's key-reuse attack — the technique (XOR two ciphertexts encrypted under the same keystream to cancel the key) applies identically here.

    SCENARIO

    A legacy system RC4-encrypts every message with the same hardcoded key. You've captured two ciphertexts, and you know the first one's plaintext was exactly "welcome back!!" (14 bytes, same length as the flag message).

    OBJECTIVE

    Recover the second message without knowing the key.

    GIVEN DATA (hex)
    C1 = 1a2b3c4d5e6f7081929394a5b6c7d8
C2 = 0f3a28415a607c96a9879fa4abd4cc

    flag{...}

    Hint 1

    Same key -> same keystream for both messages. C1 ⊕ C2 = P1 ⊕ P2 — the keystream cancels, exactly like the XOR module's Task 02.

    Hint 2

    You know P1. Compute P1 ⊕ (C1 ⊕ C2) to recover P2 directly.

    Show solution
    REASONING

    Because both messages were encrypted with the identical RC4 keystream, XORing the two ciphertexts cancels the keystream entirely (same trick as reused XOR keys), leaving P1 ⊕ P2 — and since P1 is known, P2 falls straight out.

    Summary

    • RC4 generates a keystream (KSA scrambles state, PRGA produces bytes) and XORs it with the plaintext.
    • Statistical biases in that keystream are a real, exploited algorithm flaw — RC4 is formally retired.
    • Reusing a key regenerates the identical keystream, reopening the exact same XOR key-reuse attack from module 05.
