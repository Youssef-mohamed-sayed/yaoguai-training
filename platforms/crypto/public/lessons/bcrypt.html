    Introduction

    You've now seen two very different hash functions, MD5 and (implicitly) SHA-256 — both fast, both "secure" as general-purpose hashes. So why do passwords need something else entirely? Because speed is the enemy when the input space is small and guessable, which is exactly what human-chosen passwords are. bcrypt is a hash function purpose-built to be slow — and to stay exactly as slow as you choose, even decades from now.

    History

    bcrypt was designed by Niels Provos and David Mazières in 1999, built on top of the Blowfish block cipher (Bruce Schneier, 1993). Rather than inventing a new cryptographic primitive, bcrypt's innovation was procedural: deliberately run Blowfish's key setup an expensive, tunable number of times before ever using it. It's held up remarkably well — still a recommended choice today, alongside newer alternatives like Argon2 and scrypt designed around the same idea.

    Brief definition

    DEFINITION

    bcrypt is a password-hashing function: like MD5 or SHA-256 it's one-way, but it's deliberately slow and tunable, and it automatically manages a random salt per password.

    SALT

    A random value generated per password and stored alongside its hash. Two users with the identical password get completely different hashes, which defeats precomputed "rainbow table" lookups entirely.

    COST FACTOR (WORK FACTOR)

    A configurable number — this project defaults to 12 — that sets how many times bcrypt's expensive internal key schedule repeats: specifically 2^cost iterations. Raising it by 1 doubles the time to compute one hash.

    How it works

    Password + random salt→EksBlowfish expensive key setup, 2^cost times→Encrypt fixed string with it→$2b$cost$salt+hash

    Internal mechanism — EksBlowfish

    bcrypt is built on Blowfish, but uses a modified, deliberately slow key setup ("Eksblowfish" = "expensive key schedule Blowfish") that mixes in both the password and the salt, repeatedly, 2^cost times, before the cipher is ever used. The "hash" bcrypt produces is the result of using this expensively-initialized cipher to encrypt a fixed string a fixed number of times — it's a hash function built by repurposing a cipher as a slow one-way mixing step.

    Output format

    bcrypt hashes look like $2b$12$N9qo8uLOickgx2ZMRZoHeO... — $2b$ identifies the bcrypt variant, 12 is the cost factor, followed by the salt and hash together. This is why you can verify a password later without storing the salt separately: it's embedded in the string itself.

    bcrypt in Python

    hashing.py 
    import bcrypt

def bcrypt_hash(data: str, rounds: int = 12) -> str:
    salt = bcrypt.gensalt(rounds=rounds)
    return bcrypt.hashpw(data.encode("utf-8"), salt).decode()

def bcrypt_verify(data: str, hashed: str) -> bool:
    return bcrypt.checkpw(data.encode("utf-8"), hashed.encode())
    calling it 
    h = bcrypt_hash("correct horse battery staple")
print(h)      # $2b$12$... (different every time you run this, due to the salt)

print(bcrypt_verify("correct horse battery staple", h))   # True
print(bcrypt_verify("wrong guess", h))                   # False

    Why this project doesn't reimplement bcrypt manually: every other algorithm here (DES, AES, RSA, MD5, SHA-1, SHA-256) was reimplemented from scratch and checked against known test vectors. bcrypt wasn't, deliberately — its security depends on getting Blowfish's internal setup and the expensive key schedule exactly right, and subtle bugs here don't just produce wrong output, they can silently produce a weaker hash that still looks fine. There's also a well-known historical bug class around the $2a$/$2b$ version strings and null-byte truncation. The well-audited bcrypt library sidesteps all of that.

    Strengths

    • Built-in per-password salting — no separate salt column or management needed.
    • Tunable over time — raise the cost factor as hardware gets faster, without changing the algorithm or breaking old hashes (old ones still verify at their original cost).
    • Battle-tested — over two decades of public scrutiny with no practical break.

    Weaknesses

    Implementation weakness: bcrypt silently truncates passwords longer than 72 bytes in some implementations — anything past that point is ignored, which can be surprising if you don't know about it. It also doesn't naturally resist memory-hard attacks the way scrypt/Argon2 do, since it uses a comparatively small, fixed amount of memory — making large-scale GPU/ASIC cracking farms somewhat more cost-effective against bcrypt than against newer alternatives, even though it's still far better than MD5/SHA-256 for this purpose.

    There is no meaningful "algorithm weakness" to report here the way there is for MD5 or DES — bcrypt remains a recommended, unbroken choice.

    Cybersecurity & CTF perspective

    Seeing $2b$/$2a$/$2y$ at the start of a hash is an instant signal to a penetration tester or CTF player: this isn't a fast-crackable MD5/SHA digest, so a brute-force wordlist attack (even with hashcat/John, covered next) will be dramatically slower per guess — sometimes by a factor of thousands, directly because of the cost factor. This changes real attacker strategy: against bcrypt, targeted guessing (known weak passwords, leaked password reuse, social-engineering clues) matters far more than raw wordlist throughput.

    Summary

    • bcrypt is for passwords specifically — slow on purpose, unlike MD5/SHA-256.
    • Salting (automatic, per-password) defeats rainbow tables; the cost factor defeats brute-force speedups from faster hardware.
    • It's built on a deliberately expensive Blowfish key schedule ("EksBlowfish"), not reimplemented from scratch here for good reason.
    • This closes the hashing arc: MD5/SHA for integrity, bcrypt for passwords — never the other way around.
