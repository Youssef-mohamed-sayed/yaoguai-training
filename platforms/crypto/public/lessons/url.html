    Introduction

    URLs can only safely contain a small, restricted set of characters. The moment your data includes a space, an ampersand, or a non-English letter, it has to be escaped first â€” that escaping is URL encoding (also called "percent-encoding"). It's the last encoding module before the course moves into real encryption, closing out the "representation, not protection" theme one more time.

    History

    URL encoding comes from the URI specification (RFC 1738, 1994, later refined by RFC 3986), which had to define exactly which characters were "safe" to appear literally in a web address and which weren't â€” because characters like &, ?, =, and space have special meaning in a URL's own structure (separating parameters, marking the start of a query string, etc.). Any data placed inside a URL that might contain those characters needs percent-encoding so the URL still parses correctly. It's still exactly as necessary today as it was in the 1990s, every time user input ends up in a query string.

    Brief definition

    DEFINITION

    URL encoding replaces any character that isn't safe for a URL with % followed by its byte value in hex. A literal space becomes %20 (or sometimes + in query strings specifically).

    Notice the hex you already know is doing the actual work here â€” %20 is just "%", then the hex byte value of a space (32 decimal = 0x20).

    URL encoding in Python

    encoding.py 
    from urllib.parse import quote, unquote

def url_encode(data: str) -> str:
    return quote(data, safe="")

def url_decode(data: str) -> str:
    return unquote(data)
    encoded = url_encode("hello world!")
print(encoded)              # hello%20world%21
print(url_decode(encoded))  # hello world!

    Strengths

    • Keeps URLs parseable â€” guarantees structural characters in a URL mean what the URL spec expects, not arbitrary user data.
    • Lossless and standardized (RFC 3986) â€” every web framework implements it identically.

    Weaknesses

    Zero confidentiality â€” same theme one more time: no key, instantly reversible. A URL-encoded parameter is not a hidden or protected value.

    Implementation weakness â€” double encoding and encoding confusion: if a value gets URL-encoded twice (once by mistake), or a server decodes input at the wrong layer, attackers can sometimes smuggle characters past security filters that only checked the raw (undecoded) input â€” a real class of web vulnerability called encoding/parsing confusion.

    Cybersecurity & CTF perspective

    URL encoding shows up constantly in web security: reading intercepted HTTP requests/responses (Burp Suite, browser dev tools), understanding query-string parameters in web CTF challenges, and recognizing encoding-based filter bypasses (e.g. encoding a quote or angle bracket to slip past a naive input filter that only checks for the literal character, not its encoded form). This closes out the encoding category â€” everything from here on uses a real key.
