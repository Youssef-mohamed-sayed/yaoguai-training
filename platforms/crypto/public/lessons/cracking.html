    Introduction

    Every CTF challenge in this course so far that ended with "crack this hash" quietly assumed you'd write a small Python loop over a wordlist. This final module makes that process explicit and names the real tools professionals and CTF players actually use: John the Ripper and Hashcat, plus the wordlists and lookup services (like Hashes.com) that make cracking fast at scale. This closes the course by tying every hashing lesson together into one practical skill.

    History

    John the Ripper ("John") was first released in 1996, originally to audit Unix password security, and has grown to support hundreds of hash and cipher formats. Hashcat, released in 2009, took a different angle: built from the ground up to exploit GPU parallelism, making it dramatically faster for hash types GPUs are good at (fast, unsalted hashes like raw MD5/SHA-1/SHA-256). rockyou.txt — the wordlist this course's CTF challenges have quietly relied on — comes from a real 2009 data breach of the company RockYou, which stored 32 million user passwords in plaintext; the leaked password list became (and remains) one of the most widely used wordlists in security testing, precisely because it reflects real human password choices.

    Brief definition

    DEFINITION

    "Cracking" a hash means finding an input that produces a given digest by guessing candidates and hashing each one — never by mathematically reversing the hash function itself, which (as every hashing module in this course established) isn't possible.

    WORDLIST ATTACK (DICTIONARY ATTACK)

    Trying every entry in a list of likely candidates (real leaked passwords, common words, name/date patterns) rather than every possible string.

    BRUTE FORCE

    Trying every possible combination of characters up to a given length — exhaustive, and only practical when the keyspace is small (short passwords, or a cipher with a weak key like the DES-from-PIN example earlier in this course).

    MethodGood forCost
    Wordlist / dictionaryHuman-chosen passwordsFast — only as many guesses as the list has
    Rule-based (mutate wordlist entries)Passwords close to a dictionary wordModerate
    Brute forceShort or random stringsExplodes exponentially with length
    Precomputed lookup (rainbow table / Hashes.com)Unsalted common hashesInstant, if the hash was precomputed

    How it works

    Target hash→Candidate password→Hash the candidate (same algorithm)→Compare to target→Match found = cracked

    This is exactly the loop you ran by hand in the MD5, SHA-1, and SHA-256 challenges — John and Hashcat just do it at massive scale, with the correct hash-format parsing, and (for Hashcat especially) GPU-accelerated hashing that can try billions of candidates per second for fast algorithms like raw MD5.

    Why bcrypt resists this so much better: recall the bcrypt module — its deliberately slow cost factor directly multiplies the time every single guess in this loop takes. A wordlist attack that takes seconds against unsalted MD5 can take hours or days against the same wordlist hashed with bcrypt at a high cost factor. This is the entire practical point of that lesson, made concrete.

    The password's predictability — MD5's 'brokenness' (collisions) is unrelated to cracking speed; it's MD5's raw speed plus a guessable password that matters

    Strengths

    • Legitimate defensive use — security teams run John/Hashcat against their own (authorized) password hashes to find weak passwords before attackers do.
    • Mature, broadly supported — both tools handle hundreds of hash/cipher formats, actively maintained for decades.
    • Transparent cost model — cracking speed is measurable, which is exactly what lets you demonstrate (as in Task 03) that a defensive change actually worked.

    Weaknesses — limits of these techniques

    Implementation-dependent, not algorithm-dependent: these tools succeed or fail based entirely on the target's implementation choices (fast vs. slow hash, salted vs. unsalted, predictable vs. random password) — not on any flaw in John/Hashcat themselves. A well-configured bcrypt setup with genuinely random passwords can make all of this impractically slow, which is the intended, correct outcome.

    Lookup-table services like Hashes.com only ever "know" hashes someone has already computed and indexed — they provide zero uplift against a hash of a password that's never appeared in a known breach or wordlist.

    Cybersecurity & CTF perspective

    Cracking is one of the most hands-on, high-signal skills in both offensive security (penetration testing, red teaming) and CTF competition — nearly every "crypto" or "misc" category challenge involving a leaked hash database eventually routes through exactly this workflow. On the defensive side, understanding cracking cost is how security teams justify (and measure) password policy and hashing-algorithm decisions to non-technical stakeholders: "bcrypt cost 12 makes a breach take years to exploit instead of hours" is a concrete, demonstrable claim, not a hand-wave.

    CTF Challenge

    CHALLENGE · THE FULL CHAINCTF
    SCENARIO

    A capstone chain pulling together the whole course: a leaked record was Base64-encoded, then the inner value is a hex string, which decodes to an MD5 hash of the real flag's password component.

    OBJECTIVE

    Peel every layer, then crack the final hash to recover the password, and submit it in the flag format.

    GIVEN DATA
    NWY0ZGNjM2I1YWE3NjVkNjFkODMyN2RlYjg4MmNmOTk=
    FLAG FORMAT

    flag{the_password}

    Hint 1

    Base64-decode the given string first. Look at what comes out — is it readable, or does it look like another encoding (hex, this time already in ASCII form — no further decode needed beyond that)?

    Hint 2

    The Base64-decoded result is itself the hex-formatted MD5 digest — you've seen this exact digest before, in an earlier module.

    Show solution
    REASONING

    Base64-decoding NWY0ZGNjM2I1YWE3NjVkNjFkODMyN2RlYjg4MmNmOTk= yields the literal text 5f4dcc3b5aa765d61d8327deb882cf99 — the exact MD5 digest from the MD5 module's own CTF challenge. Cracking it the same way (wordlist attack) recovers the same password.

    PYTHON
    b64 = "NWY0ZGNjM2I1YWE3NjVkNjFkODMyN2RlYjg4MmNmOTk="
hex_digest = base64_decode(b64)   # "5f4dcc3b5aa765d61d8327deb882cf99"

import hashlib
for candidate in open("rockyou.txt", encoding="latin-1"):
    candidate = candidate.strip()
    if hashlib.md5(candidate.encode()).hexdigest() == hex_digest:
        print(candidate)   # password
        break
    FLAG

    flag{password}

    Summary

    • Cracking is guessing-and-checking at scale — John the Ripper and Hashcat automate exactly the loop you wrote by hand in earlier CTF challenges.
    • Lookup services (Hashes.com) only find hashes already in a precomputed database — no uplift beyond that.
    • Cracking speed is dominated by the target's hash choice and the password's predictability, not by which cracking tool you use.
    • This closes the course: encoding (representation) → encryption (confidentiality, symmetric then asymmetric) → hashing (integrity, then passwords) → cracking (what happens when any of the above is misconfigured).
